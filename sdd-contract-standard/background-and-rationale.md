# 背景与过程问题（为什么会有这份规范）

> 本文记录 [sdd-contract-standard.md](./sdd-contract-standard.md) 的由来：一次真实 cutover
> 暴露的问题、根因、当时的处理过程，以及新方案如何从这些教训推导。供以后读规范时理解
> "每条规则在治什么病"。

---

## 1. 起源：一次真实 cutover（SPEC-027 v2→v3 正式切换）

一个用"规范驱动开发"（SDD）方式维护的 UX Proto 项目，其当前 spec（SPEC-027）在正式切换
（v2 Pack → v3 Pack，promote + 发布门禁）时，暴露了旧方案（合同 == 文档 + 按 spec 编号的验收脚本）
的系统性问题。整个过程按顺序发生了这些事：

1. **正式 authority promote** 完成（唯一的 verified commit，refs 原子切换）——这一步顺利。
2. **正式消费者流程独立验证**（bootstrap / catalog / expand / materialize / review / build）——全部通过。
3. **生成 repository-external distributions**——失败：打包白名单仍引用已删除的 v2 文件，
   版本契约仍写 `0.7.1`（正式 pack 已是 `1.0.0`）。
4. **跑权威 release gate（check-release-version.mjs）**——它按顺序运行 8 个按历史 spec 编号的
   验收脚本（check-spec0XX.mjs），逐个失败，而且**一次只暴露一个**，改完一个下一个冒出来：

   - check-spec019：断言已删除的 `ok` 字段、旧退出码 2；
   - check-spec022/023/025：断言 v2 manifest（`schemaVersion: 2` + `consumption`/`recommendations`）、
     已删除的 `inspect` 命令、已删除的 `design-language.md`、v2 关系类型（`supports`/`hard-closure`/
     `recommendation`）；
   - check-spec025：引用已删除的 v2 文件；
   - 最后停在 spec-026 的 external parity（与 v2 时代固定基线 commit 的差异）——这个差异其实是
     spec-026 自己记录的**设计内 fail-closed 检查点**，与"v2 残留"不是一回事。
5. **文档校验也挡发布**：spec-027 的 brief.md 有 3 个指向已删除 v2 资产的断链，docs 校验 fail。

## 2. 症状与根因

### S1. 真相被复制到多处 → 换代时逐个考古

一个"CLI envelope 长什么样"的事实，同时写在：spec 文档、runtime 代码、6 个验收脚本、release gate。
v3 一改 envelope，不得不到每个脚本里找 `ok`/`readyToAuthor`/`completionStatus` 的断言，
**还是一次一个地冒出来**（改完 spec-019 的 `ok`，跑出 spec-022 的 `readyToAuthor`，再跑出
spec-025 的 `design-language.md`……）。

> 根因：**duplicated truth**。同一合同事实在 N 处各写一份，任何一处换代都会漏。

### S2. 验收脚本按"历史 spec 身份"组织，而不是按"当前合同版本"组织

`check-spec0XX.mjs` 挂靠在"哪份历史 spec 写了这个功能"上。合同换代时，旧脚本不会自动退休，
而是继续对新现实报错。于是只能靠"跑一遍看它在哪一行死"来**考古**，无法静态判断哪些检查已经过期。

> 根因：验收的组织维度是**历史**（spec 编号），不是**当前**（合同版本）。

### S3. release gate 混了两个不同的问题

gate 同时回答：(a) 当前代码是否符合当前合同（机制正确性）；(b) 合同本身是否还活着（合同保鲜）。
v2 时代验收脚本的失败其实是在回答 (b)，但呈现得像 (a)。归档是对症下药，但它是**反应式**的——
需要人肉判断"这个脚本是 v2 残留还是真问题"。

### S4. 文档卫生与发布资格耦合

spec 文档断链能挡发布。这有正面价值（真的抓到了 3 个断链），但"文档卫生"和"发布资格"
是两件不同的事，耦合会让 gate 的语义变混。

### S5. 归档没有结构支持

把过期的验收脚本移出 gate = 手动改 `evaluatorPaths` 列表 + 在每个 spec 的 brief 里写状态段。
下次换代还要再做一遍，没有"结构性退休"这样的第一等机制。

### 根因总结

> **旧方案把"合同"等同于"文档"，把验收组织在历史 spec 身份上。**
> 合同换代时，文档化的合同不会自己失效，按历史身份挂靠的验收脚本不会自己退休，
> 于是每一次换代都变成对旧检查的考古与逐个修补。

## 3. 当时实际的处理过程（取舍）

1. **基线类 renewal**（确定该做）：新增 v3 Pack Git baseline 文件、更新版本契约与打包白名单、
   修正 release gate 的路径与少量机械断言（spec-018/019/024 最终全部通过）。
2. **v2 契约类检查 → 归档**（用户决策"归档为主"）：spec-022/023/025 的验收脚本是 v2 时代合同
   （v2 manifest、v2 关系类型、已删除命令）——逐条改写成 v3 语义等于重新规定"旧 spec 在 v3 世界里
   验证什么"，且 v3 机制覆盖**已经存在**（当前 spec 自己的验收套件 37/37 + spec-024 通过），
   重复劳动。于是把它们的脚本移出 gate 链、在 brief 加归档状态说明，文件保留为历史证据。
3. **spec-026 external parity**：保持为已记录的 release-decision fail-closed 检查点——这是
   spec 自己声明的"发布决策"所在，不是 v2 残留，不动。
4. **文档断链**：把指向已删 v2 资产的链接改为纯文本引用（历史叙述保留，链接移除）。

**结果**：release gate 从"红在 6 个无意义的 v2 断言上"变为"只剩一个设计内决策点（spec-026 parity）"。
但整个过程是反应式的、逐文件考古的——这正是新规范要消灭的。

## 4. 从问题到规范的推导（映射表）

| 新规范的设计决策 | 治哪个症状 |
|---|---|
| P1 真相单点：合同事实只允许一个权威载体 | S1（真相复制 → 逐个考古） |
| P2 合同即代码：可机器检查的 WHAT 进 schema/类型/行为测试 | S1 + 根因（合同 == 文档） |
| P3 版本化合同 + CURRENT 指针，不修改旧版本 | S2（换代 = 升版本，不逐个改） |
| P4 结构性退休：归档默认不运行、manifest 登记 | S5（归档无结构支持） |
| P5 验收按合同版本组织，一份套件对应一个版本 | S2（组织维度 = 当前而非历史） |
| P6 门禁数据驱动：gate-manifest，不硬编码列表 | S5 + S3（gate 语义变清） |
| P7 人类授权门：验收 PASS ≠ 发布授权 | S3 的边界（release decision 独立） |
| P8 文档不进 gate | S4（文档卫生 ≠ 发布资格） |
| §9 换代标准操作程序 | 全部（把考古变成模板动作） |

## 5. 权衡与局限（诚实的边界）

- **文档降级为决策记录会损失"验收即文档"的可读性**：有人喜欢"spec 文档里直接写验收条款"。
  本规范的选择是：可机器检查的条款进合同层，文档只留 WHY——代价是看文档看不到 WHAT，
  需要看 contracts/。
- **行为合同永远需要测试代码**：schema 不能表达顺序、失败原子性、安全边界。
  规范没有消除测试代码，只是消除"同一事实的重复断言"。
- **渐进迁移，不一步重构**：现有仓库按 §10"兼容历史"逐步抽合同、重组套件、换 manifest。
  规范对新项目收益最大，对老项目是渐进改善。
- **人类授权门是这套模式最值钱的部分**：分阶段授权、promote/release 分权、决策可追溯——
  新规范刻意保留它们，改革的只是验证层的组织方式，不是授权层的严谨。
- **活文档**：本规范自身也随实践更新；不同项目按 §9–§10 调整时，建议把调整记录回文档。

## 6. 术语表

| 术语 | 含义 |
|---|---|
| SDD | Spec-Driven Development：规范驱动开发（本项目的既有工作模型） |
| Contract-First | 合同优先验证：WHAT 以代码形式承载并作为唯一真相 |
| 结构性退休 | Structural Retirement：归档内容在工具结构上默认不参与验证 |
| Supersession | 取代：新决策/新版本声明替代旧条目，旧条目保留为历史 |
| Gate-Manifest | 门禁清单：current/required/archived 检查的数据文件 |
| Release Decision | 发布决策：版本边界、shipped-content 确认等人类独立授权点 |
